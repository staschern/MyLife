## Инцидент 06.11.2026 — периодически слетают все условные/avg-ордера

**Жалоба пользователя.** Периодически слетают все условные/лимитные (невыставленные)
ордера. Если это были ордера на ещё неоткрытые позиции — не страшно. Но если по уже
открытым позициям пропадает именно ордер на усреднение (avg) — критично: позиция
остаётся без защиты от дальнейшей просадки.

**Найденная причина (код, не предположение).** `src/Bybit/Client.php::getOpenOrders()`.
Bybit V5 отдаёт обычные лимит/маркет-ордера и условные (conditional/stop, в т.ч. наши
`avg`) по разным `orderFilter` (`Order` и `StopOrder`) — функция делает два отдельных
запроса и сливает результат. Баг был в условии пробрасывания ошибки наверх:

```php
if ($hadError !== null && empty($merged['result']['list'])) {   // было
    return ['category' => 'error', ...];
}
return $merged;
```

Если запрос `Order` успевал вернуть непустой список, а `StopOrder` (где живут ВСЕ
наши conditional/avg-ордера) в это же время падал с временной ошибкой API — условие
`empty($merged['result']['list'])` было ложным (список-то непустой, просто без единого
conditional), и функция молча возвращала `category: success` с неполным списком, в
котором отсутствовали абсолютно все условные ордера. `LiveReconciler::reconcileOrders()`
принимал отсутствующий в списке `avg`/entry-conditional ордер за «исполнен или отменён
на бирже без нас» — и:
1. Сразу помечал его `cancelled` в своей БД (ложно — ордер был жив на Bybit).
2. На СЛЕДУЮЩЕМ тике (через минуту, когда `StopOrder`-запрос уже отрабатывал нормально)
   этот же ордер снова появлялся в ответе биржи, но в локальной БД уже числился не
   `placed` — реконсайлер принимал его за «фантомный» и **реально отменял на Bybit**.

Это и объясняет «периодически», «все сразу» и «ордера на неоткрытые позиции —
не страшно, но открытые без avg — критично» — ровно то, что описал пользователь.
Интересная деталь: сама пара запросов `Order`+`StopOrder` была добавлена в
`v0.9.0-step8` именно чтобы исправить более раннюю версию этого же класса бага
(до step8 `StopOrder` вообще не запрашивался) — но при этом возник новый, более
тонкий вариант той же проблемы.

**Тот же класс риска нашёлся и у позиций.** `BybitAdapter::getPositions()` при ошибке
API тоже молча возвращает `[]` — если бы `LiveReconciler::reconcilePositions()` получил
такой пустой список при сбое (а не при реальном отсутствии позиций), он закрыл бы
**локально все открытые позиции** разом, хотя на бирже они остаются живыми — бот
перестал бы вести по ним SL/trailing/усреднение, оставаясь незрячим. Это не
воспроизведённый пользователем симптом, но тот же класс бага, исправлен заодно
(дешевле исправить сейчас, чем ждать второй инцидент).

**Исправлено, коммит [`9bda256`](https://github.com/staschern/bot.stascher.ru/commit/9bda256)
в ветку `claude/github-project-archive-4Lwio`, версия `v0.9.0-step10` → `v0.9.0-step11`:**

1. `Client::getOpenOrders()` — любая ошибка хотя бы одного из двух запросов
   (`Order`/`StopOrder`) теперь **всегда** возвращается как ошибка, не маскируется
   частичным непустым списком.
2. `BybitAdapter::getOpenOrdersOrThrow()` / `getPositionsOrThrow()` — новые методы,
   при сбое API **бросают исключение**, а не отдают `[]`. Используются только в
   `LiveReconciler` — остальные вызывающие (их 5) не тронуты, поведение не меняется.
3. `LiveReconciler::reconcileOrders()` / `reconcilePositions()` — при сбое запроса
   (поймано исключение) **пропускают реконсайл этого тика целиком**, не трогая
   локальное состояние ордеров/позиций. Следующий тик `cron_minute` (через минуту)
   повторит попытку — в худшем случае реконсайл просто отстаёт на 1 минуту, что
   безопаснее, чем ложные массовые cancel.

**Защита второго уровня — восстановление avg-ордера (по прямому запросу
пользователя, не домысливаю формулировку).** Даже если avg-ордер всё-таки пропадёт
без исполнения по какой-то другой причине (не только из-за бага выше — например,
реальная ручная отмена на стороне Bybit), `LiveReconciler::onConditionalCancelled()`
теперь для `purpose = 'avg'` не просто списывает ордер в `cancelled`, а вызывает новый
`restoreLostAveragingOrder()`:

- **Если позиция по сделке ещё открыта (`status = OPEN`)** и `manual_override` не стоит
  (пользователь не брал SL/TP под ручной контроль — именно это штатно отменяет avg,
  см. `BybitAdapter::setManualStops()`, трогать не стал) — ордер переставляется заново.
- **Хранить информацию не пришлось отдельно заводить — она уже хранится.** `trades.avg_price`
  и `trades.qty_avg` считаются один раз сразу после открытия позиции
  (`Strategy1::onPositionOpened()`, §6.4 формулы) и лежат в БД всё время жизни сделки —
  восстановление просто переставляет **тот же** ордер с теми же параметрами под новым
  `order_link_id` (старый Bybit не даст переиспользовать).
- **Пересчёт — только если данных почему-то нет.** Новый метод
  `recomputeAvgOrderParams()` дублирует формулу §6.4 из `Strategy1` (намеренное
  небольшое дублирование — тянуть сюда всю стратегию ради 10 строк было бы хуже).
  Срабатывает только для гипотетических случаев устаревших/повреждённых данных —
  на практике `avg_price`/`qty_avg` есть у каждой сделки, дошедшей до `OPEN`.
- Защитные проверки перед восстановлением: сделка ещё `OPEN` (не `AVERAGED` — второго
  уровня усреднения в s1 нет, восстанавливать уже нечего; не закрыта/отменена), нет уже
  другого живого `avg`-ордера по этой же сделке (от дублей), позиция по факту ещё
  существует на бирже (иначе `reconcilePositions()` сам её закроет).
- Событие пишется в `trade_events` (`avg_order_restored` / `avg_order_restore_failed`) —
  видно в UI бота по конкретной сделке, не только в логах.

**Все файлы прошли `php -l`.** Выделенного тестового покрытия для
`LiveReconciler`/`BybitAdapter`/`Client` в проекте нет (в `tests/` только
`RoundingTest.php`) — не писал отдельные тесты под этот фикс, слишком тонкая
интеграция с реальным Bybit API, чтобы осмысленно замокать за один заход; проверка —
по логам после деплоя (ниже).

**Инструкция для сервера** (путь на сервере не зафиксирован в системе — не домысливаю,
используйте свой текущий checkout; миграций БД нет, только код):
```bash
cd /путь/к/проекту/bot.stascher.ru
git fetch origin claude/github-project-archive-4Lwio

```
Перезапуск сервиса/демона не требуется, если бот запускается через `cron_minute`
(обычный cron, подхватит новый код на следующий тик) — если запущен как постоянный
процесс/демон, перезапустить его.

**Проверка после деплоя:**
1. В подвале/шапке веб-интерфейса бота — версия `v0.9.0-step11`.
2. В логах (`logs/`, `Logger`) не должно появляться `getOpenOrders failed` вперемешку
   с массовыми `cancelled` по нескольким сделкам сразу за один тик — раньше это была
   связка «сбой API → волна cancel»; теперь при сбое должна быть только запись
   `live_reconciler: getOpenOrders failed, пропускаем reconcileOrders на этом тике`
   без единой отмены следом.
3. Если avg-ордер всё же где-то пропадёт (смоделировать сложно без доступа к
   проду — и не нужно: случится само по себе при следующем реальном сбое API или
   ручной отмене) — в `trade_events` конкретной сделки должна появиться запись
   `avg_order_restored` с полями `avg_price`/`avg_qty`/`source` (`stored` или
   `recomputed`) и новым `order_link_id`.

**Не проверено вживую (нет доступа к серверу/проду) — ждём подтверждения
пользователя после деплоя**, как и во всех прошлых подобных фиксах по другим
проектам.
