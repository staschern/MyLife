  **Закрыто.** Корень проблемы — `.htaccess` сайта содержал классическое
  Apache-правило «всё, что не файл и не папка → `index.php`»
  (`RewriteCond %{REQUEST_FILENAME} !-f/!-d` + `RewriteRule ^(.*)$
  index.php [L,QSA]`), а в сгенерированном ISPmanager nginx-конфиге для
  PHP-FPM такого отката не было — в PHP уходило только то, что явно
  оканчивается на `.php`. Fix — добавить `try_files $uri $uri/
  /index.php?$args;` первой строкой в оба блока `location / { ... }`
  (по одному на 80 и 443 порт) в `/etc/nginx/vhosts/www-root/<domain>.conf`
  — прямой аналог Apache-правила. Применено через файловый редактор в
  самой панели ISPmanager (кнопка «Конфиг. файлы»), подтверждено `nginx
  -t` + `systemctl reload nginx`. **gotodo.ru — PHP 8.3.30/PHP-FPM,
  полностью рабочий, первый сайт мигрирован.**

  **Процессный вывод на оставшиеся 5 сайтов:** перед переключением
  обработчика каждого следующего сайта — сразу проверять `.htaccess` на

  добавлять `try_files` в nginx-конфиг до переключения, а не выяснять

  **Вторая находка на stascher.ru — реальная несовместимость с PHP 8.3**
  (не конфигурация): `stascher.ru/code/index.php` падал с `Uncaught
  ValueError: mb_http_input(): Argument #1 ($type) must be one of "G",
  "P", "C", "S", "I", or "L"`. Причина — строка `mb_http_input('UTF-8')`
  в блоке из нескольких `mb_*`-вызовов для настройки UTF-8: это
  функция-геттер (возвращает обнаруженную кодировку входных данных), не
  сеттер, её результат нигде не использовался — мёртвый код, скопированный
  по ошибке вместе с рабочими `mb_internal_encoding`/`mb_http_output`/
  `mb_regex_encoding`. В PHP 7.x неверный аргумент тихо возвращал false,
  в PHP 8+ строгая проверка типов аргументов встроенных функций бросает
  `ValueError`. Фикс — строка просто удалена (`sed -i "7d"`), поведение
  не изменилось, т.к. возврат функции не использовался. Пользователь
  подтвердил: заработало. **stascher.ru полностью закрыт.**

  **Инцидент 24.10.2026 (вечер) — 504 на всём сайте из-за включённой
  блокировки.** После включения реальной блокировки в SecurityGuard
  (см. выше) код делал `sleep(30*60)` на каждый заблокированный запрос —
  под mod_php это было мёртвым кодом (из-за старого `$is_block = false`),
  но под PHP-FPM держит воркер пула 30 минут по-настоящему. Массовое
  автоматическое сканирование (`.env`/`.git`/`config` и т.п., фоновый шум
  интернета) заблокировало десятки запросов почти одновременно — пул
  воркеров PHP-FPM 8.3 исчерпался, легитимные запросы (включая
  `/goal/diaries`) стали получать 504 Gateway Timeout. **Исправлено в два
  шага:** (1) немедленно — `systemctl restart php-fpm83` освободил
  зависшие воркеры; (2) в коде — убран `sleep(30*60)` (коммит `30d6876`),
  вместо него SecurityGuard пишет блокировку в отдельный лог
  `{корень сайта}/runtime/security_block.log` (коммит `48ade16`), который
  читает **fail2ban** (новый jail `yavdele-securityguard` на сервере,
  zero-tolerance — бан с первого совпадения, 30 минут, только по IP
  нарушителя, свой IP сервера в `ignoreip`) — теперь наказывается именно
  нарушитель, PHP-воркеры и остальные пользователи не страдают.
  Проверено end-to-end на сервере — работает.

  **Период по умолчанию:** от первой даты ведения учёта (самая ранняя
  запись движения) до текущего дня, но **не больше 5 лет** в периоде —
  если фактическая история длиннее, по умолчанию показывать последние 5
  лет, не всю историю.

  **Точки по оси времени:** брать равномерно по всему выбранному периоду,
  для старта — **50 точек**. Но **не чаще 1 точки в день** — данные
  движений хранятся в разрезе дня, чаще физически нет смысла (если
  выбранный период короче 50 дней, точек будет меньше 50, по числу дней).

  **Выбор что показывать на графике:** по умолчанию — весь капитал по
  всем фин. учётам и всем счетам в них. Пользователь может
  включать/отключать как фин. учёт целиком, так и отдельные счета внутри
  каждого учёта — прямо на странице отчёта.

  учёта и счёта, задаётся при редактировании):** отдельный флажок у
  каждого фин. учёта и у каждого счёта — учитывать ли его в графике
  капитала по умолчанию при открытии отчёта (сам факт включения/
  отключения на странице отчёта, см. выше, это не трогает — это именно
  стартовое состояние). Логика флажка, как прямо сформулирована
  пользователем, без интерпретации: **если флажок выключен — этот фин.
  учёт/счёт по умолчанию учитывается в графике.** То есть флажок — это

  правке «Сумма» «Остаток» сам пересчитывается, а можно и наоборот —
  ввести нужный «Остаток», тогда «Сумма» пересчитается в обратную
  сторону (сколько внести/списать).

  **Решение полностью на клиенте**, без правок бэкенда. Счёт-цель уже
  умел отдавать свой текущий остаток — `/fin/accounts-get` (режимы 3/4
  в `runAjax()`) раньше использовался только для надписи «(остаток)» под
  полем «Счет»/«На счет»; переиспользовал этот же запрос, добавив в его
  обработчик запоминание сырого числа (`gAccCurrentSum`/
  `gAccToCurrentSum`) и пересчёт нового поля.

  **Главная сложность — редактирование существующего движения.**
  Текущий остаток счёта уже включает эффект этого же движения (оно уже
  в БД), поэтому при открытии формы на редактирование запоминается
  исходное движение (`gOriginalEntry`: тип, счёт(а), сумма) и его эффект
  вычитается из свежего остатка — получается «остаток ДО этого
  движения» (`computeResultBaseBalance()`), от которого считается
  «будет после» в обе стороны. При копировании движения («дублировать»)
  это вычитание не делается — копия ещё не существует в БД, остаток уже
  честный. Знак эффекта — тот же, что и везде в ЯВД (`recalculateAcc`):
  расход минус, доход плюс, перемещение — минус у счёта-источника, плюс
  у счёта назначения.
